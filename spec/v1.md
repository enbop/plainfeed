# Plainfeed file format v1

Plainfeed stores durable content and reader state in ordinary UTF-8 files. The
format is intentionally small enough for people, LLMs, and producer scripts to
write without a Plainfeed-specific SDK.

## Data directory

```text
content/YYYY/MM/<entry-id>.md
state/entries/<entry-id>.toml
```

Content files are producer-owned and append-oriented. Reader state files are
server-owned and mutable. Keeping the two areas separate avoids a reader action
rewriting collected content and reduces Git conflicts.

All paths are relative to a configured data-directory root. Extra directories
and files are ignored. Entry files may be nested differently, but the calendar
layout is recommended for manageable Git trees.

## Entry document

An entry is Markdown with TOML front matter delimited by lines containing
exactly `+++`:

```markdown
+++
format = "plainfeed.entry/v1"
id = "20260717-wasip2-reader"
title = "A file-backed reader running under Wasmtime"
published = "2026-07-17T00:30:00Z"
summary = "The first end-to-end Plainfeed slice."
tags = ["plainfeed", "wasi"]
source = { name = "Plainfeed", url = "https://example.com/items/1" }
+++

The body is ordinary **Markdown**.
```

Required fields:

- `format`: exactly `plainfeed.entry/v1`.
- `id`: 1–128 lowercase ASCII letters, digits, or hyphens; the first character
  is alphanumeric. It must equal the file stem and remain stable forever.
- `title`: display title.
- `published`: RFC 3339 timestamp with an explicit offset.
- `source.name`: human-readable producer or publication name.
- `source.url`: canonical source URL. Producers should use `https` URLs when
  available.

Optional fields:

- `summary`: plain-text summary.
- `tags`: array of case-sensitive strings. Producers should prefer lowercase
  tags.

Unknown front-matter fields must be preserved by producers that rewrite an
entry and ignored by readers that do not understand them. Entry bodies may be
empty. Raw HTML in Markdown must not be trusted by a renderer.

An entry ID identifies the logical item across path changes and Git history.
Producers must not reuse an ID. Corrections may update the same file; a producer
that wants an explicit revision history should rely on Git.

## Reader state

State is TOML stored at `state/entries/<entry-id>.toml`:

```toml
format = "plainfeed.state/v1"
entry_id = "20260717-wasip2-reader"
read_at = "2026-07-17T01:00:00Z"
favorite = true

[[comments]]
id = "comment-1752714060000000000"
created_at = "2026-07-17T01:01:00Z"
body = "This pattern is useful for another project."
```

`format` and `entry_id` are required. `favorite` defaults to `false`; `read_at`
and `comments` may be omitted. Timestamps are RFC 3339. Comment bodies are
plain text in v1 and comment IDs are unique within the entry.

The server writes a complete temporary state file and renames it into place.
External tools should use the same replace-file pattern. State writers must
retain unknown keys if they perform partial updates; the v1 server owns files
it creates and currently rewrites only fields defined above.

## Ordering and compatibility

Readers order entries by `published` descending and use `id` ascending as a
stable tie-breaker. A reader must reject unsupported `format` values rather
than guessing. Compatible additions use new optional keys. An incompatible
change uses a new media identifier such as `plainfeed.entry/v2` and a new
specification.

Deletion is deliberately not defined in v1. Removing an entry file removes it
from the feed but leaves its state file harmlessly orphaned. Tombstones and
cross-producer duplicate detection are later protocol extensions.
